## Usage

```tsx
import { DateRangePicker, type DateRange } from '@acronis-platform/ui-react';
```

`DateRangePicker` is a single component that composes an
[`InputDatePicker`](/components/input-date-picker) trigger
(`pickerType="dateRange"`) with a [`Popover`](/components/popover) containing a
dual-month range [`Calendar`](/components/calendar), two editable start/end
[`InputText`](/components/input-text) fields, and a "Reset to default" / "Apply"
footer. Positioning, outside-press and `Escape` dismissal, and focus return come
from the Base UI `Popover` underneath; the grid and its keyboard model come from
`react-day-picker`. Dates are formatted and parsed with `date-fns`.

It follows a draft/commit/revert model. Opening snapshots the applied range into
a draft; editing the calendar or either text field mutates only that draft;
dismissing the popover discards it, and **Apply** is the only thing that fires
`onValueChange`. Apply is disabled while the draft equals the applied range, and
Reset is disabled while it equals `defaultValue`. A range typed end-before-start
is normalized to chronological order on commit.

This is a design-pending v1 ported from the legacy library, so it owns no token
tier: the trigger brings `--ui-input-date-picker-*` and the popup is themed by the
composed Calendar, Popover, Button, and InputText. The preset list
(All / Last 24 hours / Last 7 days / Custom range) belongs to the outer filter
composition, not to this component.

## Examples

Controlled — the parent owns the applied range and receives it on Apply:

<DemoReact>
  <DateRangePickerDemo />
</DemoReact>

```tsx
const [range, setRange] = React.useState<DateRange>({
  from: new Date(2026, 6, 1),
  to: new Date(2026, 6, 15),
});

<DateRangePicker
  label="Period"
  placeholder="Select a date range"
  value={range}
  onValueChange={setRange}
/>
```

Omit `value` for uncontrolled use. `defaultValue` is both the initial applied
range and the target of "Reset to default" — without it, Reset clears the draft:

```tsx
<DateRangePicker
  label="Period"
  placeholder="Select a date range"
  defaultValue={{ from: new Date(2026, 6, 1), to: new Date(2026, 6, 15) }}
  onValueChange={(range) => console.log(range)}
/>
```

`required`, `description`, and `error` are forwarded to the trigger, so the field
carries the same furniture and error treatment as a bare `InputDatePicker`:

```tsx
<DateRangePicker label="Period" required placeholder="Select a date range" />

<DateRangePicker label="Period" error="Please select a valid date range." />

<DateRangePicker label="Period" description="Applies to the report export." />
```

`disabled` makes the trigger inert, so the popover cannot be opened:

```tsx
<DateRangePicker label="Period" disabled placeholder="Select a date range" />
```

Both ends of a `DateRange` are optional, which is what a half-finished selection
looks like — check for `from` and `to` before using the committed value:

```tsx
<DateRangePicker
  label="Period"
  onValueChange={({ from, to }) => {
    if (from && to) fetchReport({ from, to });
  }}
/>
```

The editable fields display and parse a fixed `MMM d, yyyy` pattern (e.g.
`Jul 15, 2026`), matching the trigger. Partial or impossible input (`Feb 30,
2026`) leaves the draft untouched rather than clearing it. Locale-aware parsing
is not supported yet — a known limitation of this v1, as are the popup's
English-only "Start date" / "End date" / "Reset to default" / "Apply" labels.
