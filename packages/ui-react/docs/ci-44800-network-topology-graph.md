# CI-44800: React network topology graph implementation plan

## Purpose and status

Deliver a reusable `NetworkGraph` in `@acronis-platform/ui-react` that can be integrated into UI Builder and used to build the Auvik topology view. This plan covers the component, its contract, Figma-based examples, tests, visual regression baselines, and documentation. It also records the separate work needed to complete the UI Builder macro and the product experience, so component completion is not confused with epic completion.

**Status: library implementation and Linux visual regression checks updated.** The component, Figma-based stories, tests, ui-spec, and documentation have been updated. Product integration and Phase 2 work remain outside the library scope.

### User decisions that override earlier assumptions

- The consuming project owns the graph canvas background. The component and the Figma card-state story must not add a canvas/panel background. Individual node, status, and control surfaces still use their design tokens.
- Match Figma geometry, styles, and available tokens. When Figma uses a component that exists in ui-react or icons-react, reuse that component/icon instead of building another copy. If no equivalent exists, record the gap and implement the closest token-based treatment; do not invent a matching component.
- Cards and custom node content must stay within their bounds; details below nodes must fit and not overlap neighboring cards or connections.
- Cover both linked Figma examples, including elements under nodes and the upper-left state sheet. The state sheet must demonstrate the **real graph card rendering**, not an independently styled imitation.
- Node/edge actions must be observable in Storybook. “Show code” must display usable component examples, not Storybook `render()` functions or action-spy internals.
- This task implements the library component only. UI Builder and Auvik application integration are outside its scope.
- Accept only the current Figma styles and icons, using the corresponding ui-react components and icons-react assets. Do not implement compatibility for legacy icon names, legacy color tokens, or legacy styling.
- Canvas panning is optional and **off by default**. Only show a grab cursor when panning is enabled. Keep zoom separate from the pan setting. Pan/zoom originated in the legacy graph and earlier brief; zoom and viewport controls also appear in the supplied prototype screenshot, though not in the inspected 2029/2238 Figma frames.

## Current implementation and known gaps

The current component exports a graph with `nodes`, `edges`, and `roots`, deterministic top-down layout, node/edge click callbacks, selected nodes/paths/edges, a consumer empty state, fixed and custom text, zoom, and opt-in pan/node dragging. It uses `Card` and the React icon package, a transparent root, themed tokens, and node markers/status rows. The stories and ui-spec/docs exist.

Implemented since the initial plan: active, inactive, muted, and error markers with an accessible summary; controlled and uncontrolled branch expansion; real graph cards in the Figma state sheet; compact and expanded topology stories; node, edge, and expansion actions; optional panning; a transparent canvas; and a consumer-provided empty state. The 2029 compact story and 2238 expanded story cover the corresponding topology nodes and branches, with the expanded canvas horizontally scrollable at its Figma width.

Implemented viewport integration: the consumer can display the zoom percentage using `onZoomChange`, invoke `fit`, `zoomIn`, `zoomOut`, and `setZoom` through `viewportRef`, and use the ordinary DOM ref for browser fullscreen. A Storybook example demonstrates zoom, fit, fullscreen, and controlled expand/collapse all. Collapsing preserves the current viewport; expansion refits when necessary to keep the newly visible nodes in view. The compact Figma story presents “Connected” summary nodes only while their branches are collapsed.

Connection categories remain metadata: consumers choose the supported solid or dotted line and current design-token color explicitly. Traffic weight and animation, product-specific toolbars, UI Builder mapping, and product workflows remain outside this library task; legacy icon and style compatibility is excluded by user decision.

## Component contract and behavior

### Data and presentation

- Keep a documented TypeScript API exported from the component barrel and package entry point. At minimum, accept `graphData` with unique-ID nodes, source/target edges, and root IDs. Support title/subtitle/caption, icons, shape, card variant/device type, state, markers, alerts, and consumer metadata; preserve all node and edge fields through click callbacks.
- Document the actual `NetworkGraphNode`, `NetworkGraphEdge`, `NetworkGraphData`, `NetworkGraphProps`, selection fields, `selectedEdgeIndices`, labels, size overrides, and rendering slots rather than maintaining a partial duplicate interface in this plan.
- Keep semantic connection category and visual line pattern unambiguous. Specify precedence for category and explicit visual style, and retain a documented default for unknown categories. Do not promise legacy payload presentation compatibility.
- Use the existing icons package for current Figma icons. Document fallback behavior for unknown icons. Use current ui-react semantic tokens and avoid legacy `--av-*` tokens, legacy aliases, and hard-coded color values.
- Give consumers an explicit representation for Figma marker states, status labels and badge counts without relying solely on color. Support long text and customizable text without allowing it to paint outside its node.

### Layout and rendering

- Validate unique IDs. Build a deterministic, cycle-safe forest from declared roots; render disconnected nodes and all valid edges, including cross/back edges. Skip missing endpoints without breaking the remaining graph. Do not copy the old fixed-spacing Vue algorithm.
- Place siblings without overlap and center parents over their children. Measure complete node footprints, including marker rows, alerts, badges, and focus rings, when laying out, fitting, expanding, or collapsing.
- Fit the complete graph into its viewport initially and when graph data or dimensions change. Selection-only changes must not reset the user's viewport. Handle narrow and wide containers, varying node sizes, long strings, zoom, and dense graphs without unintended clipping or overlap.
- Match the graph in Figma 2029 and 2238: root, gateway, subnet, endpoint/networking device cards, groups, selected/error/disabled treatments, compact markers, alerts, and branch affordances. Match tokens, icons, sizes, spacing, and text without making the graph canvas opaque.
- Respect the host app's direction and light/dark theme; use appropriate logical positioning for UI controls. Avoid unsupported token names and check all referenced tokens resolve in `tokens-pd`.

### Interaction

- Enabled nodes and edges respond to pointer click and Enter/Space, expose a meaningful accessible name and visible keyboard focus, and pass the original selected item and its metadata to the appropriate callback. Separate node actions, edge actions, group expansion, and drag gestures so one does not accidentally trigger another.
- Highlight selected node IDs, selected edge indices, and shortest paths for node pairs. Document controlled versus uncontrolled behavior and what happens when arrays are cleared. State changes must not destroy a consumer's pan/zoom.
- Canvas pointer-drag pan is opt-in with default `graphDraggable={false}`; node drag is independently opt-in. Dragging must not trigger node/edge click, and enabling/disabling either option must not break keyboard or pointer activation.
- Provide zoom-in/out and wheel zoom with bounds, as in the legacy brief and screenshot. Provide accessible, localizable control labels. Confirm whether zoom controls/wheel behavior need a visibility or enablement option for consumers: the user explicitly made **pan** optional; no decision was made to hide zoom by default.
- Define how a consumer controls graph expansion, collapses/expands groups and branches, receives state changes, and invokes the page-level Expand all / Collapse all without the graph owning the page toolbar. Provide keyboard-operable affordances and accessible expanded/collapsed state.
- Document any recenter/fit, zoom level, and fullscreen integration API agreed from the prototype. Distinguish initial automatic fit from a user-invoked reset. Fullscreen can be owned by the wrapper, but it must not be claimed as supported until demonstrated.
- Provide `emptyState` or a suitable consumer slot. Demonstrate the prototype's no-topology state as **consumer-supplied** content and action; do not bake product wording into the reusable graph.

## Implementation sequence

1. **Confirm component design contract:** inspect the current Figma examples and existing ui-react components/icons; decide the library API for expansion, edge styling, and optional viewport integration. Do not implement legacy icon or style compatibility.
2. **Complete the graph API and renderer:** address the gaps above, use existing UI Kit components/icons and tokens, and preserve consumer background ownership. Keep the graph reusable and its data/callback behavior explicit.
3. **Demonstrate the integration boundary:** use Storybook callbacks and consumer-supplied content to show how an application can compose the graph; UI Builder and the Auvik product page are outside this task.
4. **Update the real examples:** make Storybook exercise the actual component for Figma 2029, the expanded 2238 topology and its state variants. Provide explicit, useful Show code snippets and observable node, edge, and expansion actions. Include Figma-based data, empty state, custom text, small viewport, and dense graph examples.
5. **Update ui-spec and docs:** reconcile the seven files in `packages/ui-spec/components/network-graph/`, generation policy, Storybook autodocs, and `apps/docs` usage/live demo with the final API, behavior, token references, integration boundary, and accessibility. Keep the Changeset accurate for the final public API.
6. **Verify and review:** execute the checks below, review actual light/dark Docker images against Figma, and document results and any explicitly deferred integration or Phase 2 work.

## Verification matrix

- Layout: one/multiple roots, disconnected/isolated nodes, empty graph, duplicate IDs, missing endpoints, cycles, cross-edges, deterministic positions, node and detail bounds, dense graphs, and resizing.
- Contract: current Figma icon and style values, unknown icon/category fallback, consumer metadata preservation, valid theme tokens, and explicit style precedence.
- Rendering: both device types and all six Figma states using **real graph nodes**; default, disabled, warning/danger and inactive markers; long/unbroken text; custom content; alert rows and accessible status names; no overflow/overlap in small viewports.
- Interactions: pointer and keyboard node/edge activation and payloads, controlled/uncontrolled selected nodes/edges, shortest path selection and clearing, disabled behavior, individual/all expansion, pan default off/on, node drag off/on, click-versus-drag suppression, zoom bounds, and selection without viewport reset.
- Consumer-facing contract: graph dimensions, consumer-provided empty content, and complete selected node/edge callback context are demonstrated within the library. UI Builder and product integration testing is outside this task.

- Stories cover Figma 2029 and 2238 with actual graph nodes, device indicators (including danger/inactive states), offline status, branch expand/collapse, actual card state matrix, edge types, callbacks, path selection, custom text, consumer empty state, opt-in pan, small viewport, and roughly 250 nodes. Make actions observable; ensure Show code is a copyable public-API example and does not display Storybook `render()` or action-spy functions.

Compare against the source frames; screenshot similarity to an existing baseline alone does not prove Figma fidelity. Avoid unrelated snapshot updates. - Verify actual pointer clicks, keyboard focus, and displayed action payloads in a browser. Check at sizes where the cards and under-node details remain readable; confirm no clipped card, status, focus ring, or viewport edge.
- Run ui-react tests, lint, typecheck and Storybook build; run ui-spec validation/conformance and generator tests; build/typecheck the docs site. Run the repository's required Docker visual update/check scripts or an equivalent targeted Docker run for both modes, and record any unrelated failure or warning honestly.
